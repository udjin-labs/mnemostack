# Проблемы recall/rerank, найденные при интеграции ConfBot / «СклерозоВ»

Версия: **mnemostack 0.4.1**. Стенд: Qdrant (точки = UUID-id), Ollama (qwen3:14b как
rerank/expansion LLM, nomic-embed-text 768d), ~25 сообщений в коллекции.
Найдено при отладке поиска по истории чата. Все пункты воспроизведены инструментально.

---

## 1. [CRITICAL] Reranker — молчаливый no-op при длинных/UUID id

`Reranker.rerank` строит промпт со списком кандидатов и просит LLM **вернуть id**
релевантных. `_parse_ids(resp.text)` затем матчит их к `id_map`. 

Проблема: когда `id` кандидатов — **длинные UUID** (а это дефолт для Qdrant-точек),
модель не воспроизводит их точно → `_parse_ids` возвращает пусто/частично →
срабатывает graceful-fallback `return results` (исходный порядок). **Реранкер не
делает ничего и не сигналит об этом.**

Воспроведение:
- 5 кандидатов с id `"1".."5"` → реранк корректно переупорядочивает (ставит
  релевантные на #0/#1).
- 25 реальных кандидатов с UUID-id → возвращается ровно входной порядок (детерминированно,
  3 прогона подряд идентичны).
- Те же 25 кандидатов, но с короткими целочисленными id → реранк начинает
  переупорядочивать (для части запросов).

Влияние: в типовой конфигурации (Qdrant + UUID) **LLM-реранк фактически выключен**,
о чём ничто не предупреждает. Вся «vector→rerank» цепочка молча деградирует до RRF-порядка.

Идеи фикса:
- Внутри `rerank` ремапить кандидаты на короткие порядковые id (`0..N-1`) для промпта,
  а после парсинга мапить обратно. (Снаружи я так и обошёл — помогает.)
- Либо просить LLM вернуть **позиции/номера строк**, а не сырые id.
- Логировать WARNING, если `_parse_ids` вернул < ожидаемого (см. п.3).

## 2. [HIGH] `max_tokens=200` на выводе реранка не масштабируется с N

`Reranker.__init__(max_tokens=200)`, вызов `llm.generate(prompt, max_tokens=200)`.
Комментарий в коде: «rerank returns just IDs, 200 is enough». Для N кандидатов с
UUID-id список id легко превышает 200 токенов (25×UUID ≈ 350+ токенов) → вывод
обрезается → парс неполный/битый → fallback. Усугубляет п.1.

Идеи фикса: `max_tokens` ∝ числу кандидатов (напр. `max(200, N*8)`), или вынести в
параметр и документировать зависимость от формата id.

## 3. [HIGH] Тихий fallback скрывает отказ реранка

При непарсе `rerank` логирует на уровне **debug** («returned no relevant ids») и
возвращает вход. На практике реранкер может быть полным no-op без единого видимого
сигнала — баг был невидим до ручной трассировки по стадиям. 

Идеи фикса: WARNING при пустом/частичном парсе; счётчик «сколько id из N
распознано»; опционально — флаг strict, кидающий исключение.

## 4. [MEDIUM] Длинные тексты кандидатов раздувают промпт реранка

Полные тексты сообщений (900–1700 символов × N) уходят в промпт целиком. Вместе с
п.1/п.2 это снижает надёжность. Для суждения о релевантности достаточно сниппета.

Идея фикса: внутри реранка усекать текст кандидата до ~300–500 символов (снаружи
помогает — реранк стабильнее на сниппетах).

## 5. [MEDIUM] RRF топит вектор-сильные, лексически-бедные результаты

Сообщение с **вектор-рангом #2** (cosine 0.721) после RRF-слияния с BM25 оказалось на
**#14**: BM25 не нашёл лексических совпадений (запрос «правила пользования ботом» vs
разговорная реплика) и утянул объединённый ранг вниз. `adaptive_weights=True` это не
скомпенсировал. Для семантических запросов со слабым лексическим перекрытием BM25
**активно хоронит** релевантное, а сломанный реранк (п.1) уже не вытаскивает.

Идеи фикса: floor для vector-top-K (гарантировать попадание в кандидаты реранка);
сильнее понижать вес ретривера, чьи скоры «плоские»/неинформативны на данном запросе;
диагностический лог итоговых весов adaptive_weights.

## 6. [LOW / suspected] Дрейф query_expansion на размытых запросах

Подозрение (не изолировал так же чисто, как 1–5): на размытых/мета-запросах
expansion расширяет в сторону доминирующих тем корпуса, поднимая нерелевантное.
Стоит проверить отдельно — возможно, стоит гейтить expansion по длине/специфичности запроса.

### Сводно
Главная связка: **#1+#2+#3** — LLM-реранк в реальной (Qdrant/UUID) конфигурации молча
не работает и не сигналит. Из-за этого качество держится только на RRF, а его перекосы
(#5) ничем не исправляются. Минимальный высокоэффективный фикс: ремап id на короткие
порядковые + масштабирование `max_tokens` + WARNING при непарсе.

## Идея фикса для #5 (vector-floor) — проверено, работает

Против «утопления» вектор-сильных результатов: гарантированно подмешивать в финальный
набор **вектор-топ-N по сырому cosine** (поверх RRF/rerank-результата, без дублей).

Логика: RRF/реранк могут закопать сообщение с высоким косинусом, но слабым лексическим
перекрытием; «пол» из вектор-топ-N не даёт ему утонуть. Генератор-LLM разбирается с
лишним контекстом, а на edge-запросах (ответа в данных нет) ложных срабатываний это НЕ
добавляет.

Воспроведено в ConfBot (обход на стороне приложения, `vector_floor=5`):
- «правила пользования ботом» (вектор-#2, RRF-#14): без флора → «не нашёл»; с флором → корректный ответ.
- «Кто написал про фишинг» (вытягивался реранком): с флором не сломался — автор по-прежнему верный.
- Edge «зарплата у новых» (нет в данных): с флором по-прежнему «не нашёл» — ложного ответа нет.

Предложение для модуля: опция `vector_floor: int` в Recaller/пайплайне — после слияния и
реранка догарантировать присутствие top-N по чистому вектору. Дёшево, надёжно, ортогонально
починке реранка (#1–#3).

## Обратная связь по 0.4.2 (проверено на ConfBot)

Спасибо — реранк теперь делает короткие prompt-id + усечение текста (#1/#4 закрыты), и
появился `vector_floor` (#5) и логи реранка (#3 закрыт). Два наблюдения по итогам прогона:

**A. `vector_floor` применяется PRE-rerank → его снова топит срез top_k.**
В 0.4.2 floor мерджит сильные вектор-кандидаты в recall ДО реранка. Дальше реранк + срез
до top_k снова выкидывают вектор-сильное-но-лексически-бедное сообщение. Симптом: запрос,
где нужный текст имеет высокий косинус, но низкий RRF/лексику, опять даёт «не нашёл».
У нас в ConfBot пришлось вернуть POST-rerank floor (гарантированное присутствие top-N по
вектору ПОСЛЕ реранка и среза). Предложение: применять floor (или хотя бы часть его) после
реранка / выводить floored-кандидаты за пределы top_k-среза.

**B. Реранк парсит очень мало id даже с короткими prompt-id.**
Логи: `rerank parsed 2 of 25 candidate ids`, `1 of 25`, иногда `produced no usable ids,
keeping original order`. Т.е. LLM (qwen3:14b, think=false) возвращает 0–5 id из 25 — реранк
часто почти no-op. Возможно: модель отдаёт только «явно релевантные» и режет остальное;
либо стоит просить ПОЛНЫЙ переупорядоченный список позиций, а не подмножество id, и/или
поднять output budget. Стоит посмотреть промпт/парсинг.

## РЕШЕНО в 0.4.3 (проверено на ConfBot) ✅

Спасибо! A и B закрыты:
- реранк масштабирует output budget (`effective_max_tokens = max(max_tokens, len(head)*10)`) —
  `no usable ids`-фоллбэков на нашем наборе больше нет, парсинг стабильнее (B);
- `vector_floor` доходит до финала — вектор-сильное-лексически-бедное сообщение больше не
  тонет в реранке/срезе (A).

ConfBot перешёл на 0.4.3 и **убрал свой страховочный POST-rerank вектор-флор** — модуль
справляется сам. Регрессия (правила-пользования, как-задать-вопрос, MY.GAMES, фишинг-автор,
2 июня, тимбилдинг, edge) проходит на чистом 0.4.3 без обходов.
