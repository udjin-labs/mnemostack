# mnemostack — предложения и находки со стенда ConfBot/СклерозоВ

Источник: эксплуатация mnemostack в боте памяти чатов (Yandex Messenger, русский
корпус, Ollama-локально). Это костыли, которые мы держим у себя, но которые имеют
смысл как **общеполезные** продуктовые фичи (не узко под наш кейс), плюс находки
из валидации 0.4.8/0.5.0.

Статусы на момент написания: vector_floor, describe_image, prompt_overrides+category,
abstention_text — уже в релизах. Ниже — то, что ещё в работе/обсуждении.

---

## A. Общие фичи (по убыванию польза/стоимость)

### A1. Контроль «думанья» / generation options у LLM-провайдера  ⭐ самый общий
**Костыль:** сабкласс `OllamaLLM`, вшивающий `think:false` в payload. Без него
reasoning-модели (qwen3/qwq/deepseek-r1 и любые «думающие») тратят весь
`num_predict` на размышления и возвращают пустой ответ → реранк/экспансия/extract
падают в фолбэк. Сейчас `OllamaLLM.generate` шлёт в `options` только `temperature`
и `num_predict` — другого пути нет.

**Почему общее:** бьёт каждого, кто берёт mnemostack + Ollama с современной моделью
(сейчас это почти дефолт). Не про наш домен — про сам провайдер.

**Форма:**
- `options={...}`-passthrough (num_ctx, top_p, и т.д. — всё, что понимает Ollama);
- отдельный `think: bool | None = None` (в Ollama API это top-level поле, не в options);
- провайдер-специфично (не в базовый `LLMProvider` — у Gemini своя механика thinking
  budget), как уже сделано с `describe_image`.

**Эмпирика по дефолту (проверено на стенде, qwen2.5vl=не-thinking, qwen3:14b=thinking):**
```
think=false → HTTP 200 и на не-thinking, и на thinking      ✅ безопасно везде
think=true  → HTTP 400 "does not support thinking" на не-thinking  ❌
без think    → HTTP 200                                       ✅
```
**Вывод:** ошибается только `think=true`. `think=false` не ошибается нигде, поэтому
**можно ставить `think=False` дефолтом сразу** — авто-ретрай/«дефолт вторым шагом»
избыточны (наш реальный сбой был не ошибкой, а тихим выжиганием бюджета → пустой
ответ; чинить нечему). Семантика: `None`=не слать, `False`=безопасно везде,
`True`=только если модель поддерживает (тут — опционально авто-ретрай без think).

### A2. Метаданный/партиционированный фильтр на всех поверхностях recall  ⭐ мульти-тенантность
**Костыль:** фильтруем выдачу по `chat_id` **в Python после recall**
(`[r for r in recalled if payload.chat_id == x]`) + структурный scroll по author/time
вместо similarity.

**Почему общее:** мульти-тенантность/неймспейсы (per-user/-tenant/-project память) +
структурные запросы «что писал X / за неделю» — универсальная потребность.

**Уже в ядре, но дыры (подтверждено по коду):**
- `Recaller.recall(filters=)` существует и нативно проталкивается в Qdrant
  (`vector.search(filters=)`, включая gte/lte-диапазоны) — **но не выведено** ни в
  `recall_flow`, ни в HTTP `/recall`, ни в MCP, ни в CLI → прод фильтрует в Python.
- **`BM25Retriever.search` принимает `filters` и молча игнорирует** → в fused-выдаче
  с фильтром vector-кандидаты отфильтрованы, а BM25 подмешивает чужие. Это **не
  «нет фичи», а изоляционная утечка между тенантами** — тестировать адверсариально
  как data-isolation, а не как ранжирование. (Нас спасает только Python-постфильтр.)

**Форма / нюансы:**
- довести `filters` до всех 4 поверхностей + честная семантика на каждый ретривер;
- BM25 фильтровать **до** отбора top-K, а не после скоринга: постфильтр после top-K
  недонабирает (просишь 40, скорнул 40, выкинул чужие → вернулось <40 → теряется
  recall). Фильтровать кандидатное множество, потом скорить.

### A3. Проекция payload-полей в answer-контекст + enrichment-хук на ингесте
**Костыль:** подпись картинки (VLM) вшиваем **в `text`**, а не в payload — иначе она
не видна промпту ответа. `dates_answer` отделяет даты в тексте от дат публикации.

**Реальная дыра:** payload-поля сейчас **не видны answer-контексту** (он показывает
только source/timestamp). `IngestItem.metadata` уже едет в payload — обогащать на
ингесте библиотечный пользователь может сам.

**Форма — разбить на две части (4a дешевле и важнее):**
- **A3a: `context_fields=[...]` у генератора ответов** — проекция **уже существующих**
  payload-полей в промпт. Дёшево, **без переиндексации**, закрывает основную боль
  немедленно.
- **A3b: `Ingestor(enrich=callable)`** — обогащение на ингесте (даты/суммы/сущности).
  Требует переиндексации; плюс закрыть CLI-путь индексации файлов и оконные чанки
  (обогащать собранный текст окна). Граница «механизм в core, экстрактор ваш» — та же,
  что для промптов; языкозависимые экстракторы (даты и т.п.) в core НЕ тащить.

### A4. Переписывание follow-up'ов (разрешение местоимений/эллипсиса) — последним
**Костыль:** `rewrite_followup(prev_q, prev_a, query)` — «а кто это написал?» →
самостоятельный вопрос, перед recall.

**Почему общее, но низкий приоритет:** любой разговорный RAG спотыкается на
контекстно-зависимых вопросах; но это единственный пункт, который пользователь и
сегодня делает одной LLM-строчкой у себя. История диалога у mnemostack не живёт (и
не должна) — значит это не стейт/стадия, а опт-ин helper `rewrite_followup(query,
history, llm)` (языконейтральный). Ценность нетривиальной части — в **триггер-эвристике**
(не переписывать самостоятельные вопросы — иначе лишний вызов и порча хороших
запросов) + выверенном промпте, а не в самом вызове.

**Приоритет (польза × стоимость):** A1 → A2 → A3a → A3b → A4.
(A1 поднят к верху: тоже «тихо врёт» — пустые ответы у большинства локальных юзеров —
но стоит один параметр против работы A2 по 4 поверхностям.)

## B. Находки валидации list_extract (count/list-рецепт) на русском корпусе

Контекст: проверяли `AnswerGenerator(list_extract_mode=True, prompt_overrides={...},
abstention_text=...)` с русскими шаблонами на нашем корпусе (~31 сообщение).

**Работает:** override доезжает (в `_generate_list_extract` читается
`prompt_overrides.get("list_extract"/"list_finalize")`); `abstention_text` локализует
фолбэк (англ. «Not in memory.» больше не течёт); `category=` обходит англоклассификатор.

**Не работает надёжно (и это НЕ промпт — доказано трейсом):** тот же промпт и те же
31 сообщения в контексте то дают 3 верных элемента, то `{"items":[]}` → абстейн.
Результат зависит от **порядка** в пуле (недетерминированный recall с LLM-экспансией)
и от прогона к прогону: на одном пуле опросы 0/5, на другом 1/1; count нестабилен;
finalize **перефразирует/искажает** русский вместо дословной сборки.

**Просьбы к core (3 пункта):**
1. кормить `list_extract` **переранкованным** пулом, а не сырым recall (или ранжировать
   внутри) — порядок входа решает, теряются элементы вне верхушки окна `[:40]`;
2. **retry extract при пустом** результате до абстейна (пустой extract сразу абстейнит;
   `inference_retry`, похоже, не покрывает list-путь);
3. **finalize — дословная сборка** (или пропуск, если items уже чистые); сейчас второй
   проход переписывает текст.

**Наш статус:** в прод двухпроходку НЕ берём — нативный одно-проходный генератор с
реранк-контекстом берёт те же элементы стабильно (3/3, ~5с) и без искажений.
Mnemostack-рецепт — опция на большой корпус, когда приедут пункты 1–3.
